# 选型口径：怎么判断一个记忆系统能不能用

> 凯瑞在 EigenFlux 对话里的建议（2026-11-07）：把选型标准写进文档。
> 顺序就是优先级：**来源可引用 > 状态隔离 > 可审计 > MCP 接入**。
> 这是判断标准，不是排名——77 系统横评没有原始分表，任何跨系统排名
> 都不引用、不认领（见 §5）。

## 1. 来源可引用（最优先）

每条记忆必须能追溯到它的来源：谁说的、在哪说的、凭什么说的。
没有来源的记忆是一句断言，不是事实——无法核实、无法纠正、无法删除。

Stellamem 的做法：

- 每条 claim 带 provenance（`record_id` / `session_id` / `source_ref`），
  证据字段 `evidence` + `evidence_verified` 标记；
- 逐题追踪表（`benchmark/longmemeval/tracking_table_20261106.csv`）把
  source turn → claim → 审批 → 检索候选 → 投影 → 回答/拒答整条链记下来，
  五处有无逐题可查；
- 提取时无 claim 的 gold turn、审批拒绝的记录，都有明确的断点归属，
  而不是沉默消失。

一票否决项：记忆说不出处。来源不可引用的系统，召回分数再高也不采纳。

## 2. 状态隔离

不同主体（user / persona / viewer）的记忆绝不混放；跨主体只有桥一条路，
默认拒绝、全文人工批准。

Stellamem 的做法：

- 主体绑定（PR #64）：全部 5 个 MCP 工具 + CLI + 环境变量绑定，
  别名归一化，无效值启动即失败；
- 每主体独立文件与独立 tallies（PR #67 投票、PR #68 桌面页、PR #70 日档）；
- 桥是唯一通道（`compiler/bridge.py`），三类结构化模板、无自由文本字段，
  过期 fail-closed；每次访问带双向审计行（PR #86）；
- 多客户端隔离自审：31/31 自定义探针 + 242 隔离测试通过（2026-11-06），
  唯一发现的存在性预言机缺口由 PR #73 修掉。

一票否决项：跨主体泄漏。隔离做不到的系统，接入再方便也不采纳。
（注：DSH 的 MCP 启动绑定仍是部署缺口，见关门清单第①条——
仓库侧已做完，宿主侧未改；对外不宣称“彻底完成”。）

## 3. 可审计

每个决定留一张可查的票。没有审计，§1 和 §2 是否成立就无从查证——
可审计不是 §1、§2 的替代品，是让它俩可验证的手段。

Stellamem 的做法：

- append-only version chain + review log（每条审批、每次自动批准、
  每次撤回都留痕，`approved_via: "auto"` 可区分）；
- guardrail 回执（PR #86）：护栏 id、判定 class、规则摘要 digest，
  digest 可由回执自身字段重算验证；
- 桥双向审计行（PR #86）：谁 / 哪个主体 / 读还是写 / 命中还是拒绝；
- 夜间结算报数（PR #63）：每晚 23:30 按主体报条数，条数对不上即发现丢失。

## 4. MCP 接入（最后）

任何客户端都能通过标准协议用上它。排最后的原因：记忆本身不可引用、
会泄漏、不可审计时，接入再方便也没有意义；而且 MCP 只是接入方式之一，
不是唯一方式（还有 HTTP API 与 JS 适配器）。

Stellamem 的做法：MCP 服务器（stdio，5 个工具）+ HTTP v1/v2 API +
OpenClaw 适配器；当前宿主是 DSH，愿景是全部模型/客户端都能用。
（OpenClaw 不在愿景中心：2026-11-06 用户已明确，不要只搞 OpenClaw。）

## 5. 怎么用这套口径（与不做什么）

- 按顺序卡：§1 或 §2 不过，后面再好也否决；§3 不过，§1、§2 的宣称
  一律按“未验证”处理；§4 只在前三项通过后比较。
- 不做跨系统排名：凯瑞纠正过的证据边界——77 系统横评没有原始分表，
  Stellamem 的公开数字（LongMemEval 0.350 / 召回@5 0.870 / 拒答 0.800）
  只用于同跑道臂间比较，不用于跨系统排名。任何人拿这套口径去排别的系统，
  须先拿到对方同口径的原始证据。
- 口径本身也要被审计：每项后面的“Stellamem 的做法”都指向代码与测试，
  不是形容词；做法变了，文档跟着改。
