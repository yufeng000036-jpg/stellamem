# Stellamem · 星忆 — Use Cases / 使用场景

> 「给 AI 记忆一个 Git。」
> A local-first, auditable memory governance layer for AI agents.
>
> **状态：Alpha（v0.2.0-alpha），未达到生产可用。** 本文如实区分「现在能用」与「路线图」，
> 不承诺尚未实现的能力。

---

## 先说清楚：Stellamem 解决的是什么问题

大多数「AI 记忆」的做法是：把聊天记录存起来，下次原样塞回去。

这带来三个后果：

1. **记的多不等于记得准** —— 原始对话里既有事实，也有情绪、玩笑、一次性猜测。全部塞回上下文，
   噪音会盖过信号。
2. **改了也说不清** —— 记忆被覆盖后，没人知道原来是什么、为什么改、能不能退回去。
3. **不该记的也被记了** —— 密钥、证件号、隐私，一旦进了记录就很难清理。

Stellamem 不用「存聊天」的思路，而是走治理的思路：

```
对话
  → 来源指针（source pointer，只记「在哪儿说的」，不复制原始转写）
  → 主张抽取（claim extraction）
  → 安全策略（secret gate + 敏感/身份分级）
  → 关系引擎（NEW / DUPLICATE / REINFORCES / REFINES / COMPATIBLE /
              SUPERSEDES / CONTRADICTS / UNCERTAIN）
  → 人工审核收件箱（review inbox）
  → 规范化 Markdown 记忆
  → 上下文投影（context projection，只注入与当前任务相关的已批准主张）
```

一条**主张（claim）**带有：`kind`、`subject`、`scope`、`predicate`、`value`、
`confidence`、`evidence`、`provenance`。

几条贯穿所有场景的设计原则：

- **Memory is not a dump.** 记忆不是垃圾桶，不是对话的复制品。
- **Secret is not memory.** 密钥在**任何模型调用之前**就被拦截。
- **Sensitive is not auto-write.** 敏感与身份类主张从不自动写入，必须走人工审核。
- **Memory must have provenance.** 来源指针解析不了就**抛错**，绝不编造出处。
- **Conflict must not disappear.** 冲突不静默覆盖，一律留痕。
- **Users own their memory.** 记忆可查看、可修正、可删除。

## 1. AI Companion（长期陪伴）

**目标**：让 AI 从「第一次认识」走到「持续的共同经历」，再走到「理解你的变化」。

这条路径分四步：

| 阶段 | 记忆里应该有什么 | 现在 / 路线图 |
|---|---|---|
| 第一次认识 | 基本偏好、称呼、交流风格 | ✅ 现在可用（主张 + 审核） |
| 持续聊天 | 反复出现的事实被 `REINFORCES` 累积，而不是重复存多份 | ✅ 现在可用（关系引擎） |
| 形成共同经历 | 有出处的经历片段 + 那次当时的状态 | ⚠️ 部分可用；蒸馏/长期保留**未实现** |
| 理解变化 | 旧主张被 `SUPERSEDES` / `REFINES`，而不是被覆盖抹掉 | ✅ 现在可用（版本链 + 回滚） |
| 关系连续性 | 跨会话把「这个人是谁、我们经历过什么」投影回上下文 | ✅ 现在可用（受字符预算限制） |

**对使用者最关键的三点保证**：

- **记忆可查看、可修正、可删除。** 记忆就是本地 Markdown 文件，你能打开、能改、能删。
- **敏感信息有保护。** 密钥类内容在模型调用之前被拦截；敏感与身份类主张不会自动写。
- **控制权在你手上。** 人工审核收件箱把「要不要记住」这个决定留给你，而不是交给模型。

**如实说明**：完整的「共同经历」叙事化沉淀（把一段时间的互动提炼成一段可读的关系史）
目前**没有实现**；当前是主张级治理，不是叙事级记忆。上下文投影依赖关键词检索，
**可能漏召回**。

## 2. Personal AI（个人助手 / 第二大脑）

适合：个人偏好、习惯、长期项目上下文、常用决策依据。

- 偏好类主张（喜欢什么、讨厌什么）走审核后入库，后续被 `REFINES` 逐步细化。
- 项目上下文按 `scope` 分区，避免「家里的偏好污染工作场景」。
- 上下文投影按任务相关性注入，并有全局字符预算，防止把上下文塞满。

**现在可用**：主张抽取、分区、审核、投影。
**路线图**：保留策略与蒸馏（哪些记忆该变冷、该合并、该退休）——**尚未实现**。

---

## 3. Coding Agents（工程记忆）

适合：工程决策、架构规则、代码风格、历史 Bug、项目约定。

这是 Stellamem 结构上最契合的场景之一，因为工程记忆天然是「有出处的断言」：

- 架构规则 → 高 `confidence` 主张，进入长期记忆。
- 代码风格 → `scope` 绑定到某个仓库/语言。
- 历史 Bug → 带 evidence 与 provenance（哪次提交、哪个决策、为什么）。
- 项目约定 → 与规则冲突时记 `CONTRADICTS`，等人类裁决，而不是让 Agent 自己拍。

**为什么「不要静默覆盖」在代码场景特别重要**：架构决定往往有当时的约束条件。
如果新决定直接覆盖旧决定，半年后就没人知道当初为什么那样写。Stellamem 保留冲突日志
与版本链，可以回滚。

**现在可用**：主张模型、关系引擎、冲突日志、事务回滚与崩溃恢复。
**⚠️ 不适合**：当作团队共享的权威知识库——它还没有多用户/权限模型，也没有远端同步设计。

## 4. Education（AI 学习伴侣 / Tutor）

适合：记住学习阶段、已掌握内容、易错点、个人偏好。

- 「已经掌握」→ 主张，可被 `REFINES` 细化（比如「会基础语法但不会闭包」）。
- 「易错点」→ 带 evidence，反复出现时 `REINFORCES`。
- 「偏好」→ 讲解风格、节奏、举例类型。

**重要限制（如实说）**：本地 4B 模型在 **kind 分类上存在漂移**，也就是「这句话属于哪类
记忆」有时会判错。在教育场景这类细粒度区分（事实 / 易错点 / 偏好）要求较高的用法里，
**必须依赖人工审核收件箱兜底**。

**现在可用**：主张 + 审核 + 投影。
**未实现**：学习进度结构化图谱、遗忘曲线调度、测验生成。

---

## 5. Local AI（本地模型 / 离线场景）

Stellamem 的核心是**只有 Python 标准库**的、框架无关的实现。适配器是插件式的。

- **远程云模型不在支持范围**：仅支持 **loopback（本机）** 模型服务。
- 本地模型意味着：对话内容不出本机，记忆治理也在本机完成。
- 好处是隐私边界清晰；代价是模型能力受限，需要更依赖人工审核。

**现在可用**：loopback 本地模型 + 完整治理管线。
**路线图**：更多本地推理后端的适配器。

---

## 6. Game / NPC（游戏角色记忆）

适合：NPC 记住与玩家的互动、世界观内的事实、玩家做出的选择。

这是**明确的路线图场景**，不是当前能力：

- 设想中：玩家的关键选择成为主张，冲突选择走 `CONTRADICTS` 而不覆盖，
  可回滚到某个存档点的记忆状态。
- 设想中：`scope` 绑定到某个存档 / 某条剧情线，避免跨周目串味。

**现状**：核心治理逻辑是框架无关的，理论上可以作为游戏服务的记忆层，
但**没有任何游戏引擎集成，也没有做过游戏场景验证**。请当作方向，不要当作功能。

---

## 7. Enterprise Agent（企业 Agent）

适合：需要「可审计、可追溯、可回滚」的组织级 Agent 记忆。

Stellamem 的设计原则正好对应审计需求：每条记忆有出处、冲突有记录、改动可回滚。

**但这块限制最多，必须说清楚**：

- **Alpha，非生产可用。** 不要把它放进关键业务链路。
- **没有多用户 / 权限 / 租户模型。**
- **远端云模型不支持（仅 loopback）。**
- **没有 GUI**，一切基于文件与命令行。
- **没有外部长期用户验证。**
- **蒸馏与保留策略未实现**，长期运行时的记忆膨胀问题尚未解决。

如果你在做企业方向，现在合适的姿态是：**参与设计讨论、提 issue、在实验环境验证**，
而不是部署。

## 场景总览表

| 场景 | 现在可用 | 部分可用 | 路线图 |
|---|---|---|---|
| AI Companion | 偏好、反复强化、版本链、投影 | 共同经历沉淀 | 叙事化关系史 |
| Personal AI | 主张、分区、审核、投影 | — | 蒸馏 / 保留策略 |
| Coding Agents | 决策、规则、冲突日志、回滚 | — | 多仓库/团队协作 |
| Education | 主张 + 审核兜底 | 易错点累积 | 学习图谱、遗忘调度 |
| Local AI | loopback + 全管线 | — | 更多本地后端 |
| Game / NPC | — | 核心逻辑框架无关 | 引擎集成、场景验证 |
| Enterprise Agent | 审计友好的底座设计 | — | 权限模型、GUI、生产加固 |

## How to contribute / 如何参与

项目处于 Alpha，**最有价值的贡献是使用反馈与反面案例**：

- 报告「这条记忆不该被记住」或「这条记忆被漏掉了」的具体例子。
- 报告 kind 分类错误（尤其是本地 4B 模型）。
- 讨论关系引擎的边界：`REFINES` 和 `SUPERSEDES` 什么时候该用哪个。
- 补充你所在场景的需求描述，帮助我们判断优先级。
