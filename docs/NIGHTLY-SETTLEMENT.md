# 夜间结算报数（2026-11-05）

每天一次、看得见的记忆自报，替代后台重建的静默运行。
模块：`compiler/nightly_settlement.py`，CLI：

```bash
python compiler/nightly_settlement.py --root <记忆数据根目录> [--db <索引库路径>] [--votes <投票文件路径>]
```

报告打到 stdout，同时写当日日志与基线状态文件（默认
`<root>/system/nightly-settlement/`）。该目录不在索引指纹范围里，
结算本身不会让索引变旧。

## 报什么

四个数（定义见模块 docstring）：

1. **各层几条**：active 记录按主体 × 类型计数。user 主体分
   preference / lesson / decision / project / fact + 其他；
   persona / viewer 只报总数，不报内容；pending（inbox 未审）单列；
   superseded / rejected 只计入“历史”，不进各层。
2. **桌面多少字节**：按主体报桌面页真实字节数（见 `docs/DESKTOP-PAGE.md`）；
   没有桌面页的主体不报，全部没有时报“未启用”，不编数。
3. **今晚动了几条**：自上次结算以来写入链（`system/version-chain.json`）
   新增的事件数。基线存在上次结算的状态文件里（时间戳 + 事件总数）；
   首次运行没有基线，报“首次结算、无上次基线”，不猜。
4. **日志叫什么**：本次结算日志的文件名与路径。

另附两行状态：后台重建最近一次成功还是失败、索引行数与生产库最后写入时间。
后台重建的状态：服务对象在场（同进程）时用它的真实失败记录；冷启动的 CLI
没有那个进程，只能用索引新鲜度推断，措辞上不把推断说成实测。

另附一节“命中投票”（`--votes` 给出投票文件路径时才有；不给或文件不存在
时报“未启用”）：今日 / 累计命中数（分主体，自动/手动分开）+ 命中最多的
主体 × 类型（仅主体 + 类型 + 次数，不含记录 id 与正文）。投票文件损坏时
结算失败，不报不准的数。详见 `docs/HIT-VOTES.md`。

## 只读边界

- 只读记忆文件与写入链；只写结算日志与基线状态文件。
- 绝不写记忆库、不改任何记录、不碰注入策略、不碰主体隔离与桥治理。
- 管理文件读不懂、写入链或基线文件损坏时，本次结算直接失败
  （CLI 非零退出，不写日志、不更新基线），绝不拿不准的数当真的报。
- 日志与基线写文件时先写同目录 tmp 再改名，写一半断电不留半个文件。

## 部署

并进 DSH 每天 23:30 健康检查，不另起夜间任务。接线是 PC 上的本地任务，
不在本 PR 范围。验收口径：连跑 7 晚不缺席；四个数抽查跟手工数对得上；
后台重建失败时报告里能看见。

  项目名与仓库链接未知，来源待补）
- **采用的功能**：“夜间结算报四个数”的做法——夜里跑一遍，最后报各层几条、
  桌面多少字节、今晚动了几条、日志叫什么
- **为什么采用**：Stellamem 的后台重建是静默的，状态只有出问题才被发现；
  每天能看得见的自报正是缺的那块，成本只是一次只读统计
- **我们的适配与差异**：原版是单主体、固定 22:05、桌面页已有。我们改成
  双主体（user 分类型计数，persona / viewer 只报总数，不报内容）、
  并进已有的 23:30 健康检查、桌面未做先报“未启用”不编数；
  “今晚动了几条”用 append-only 写入链 + 基线状态文件精确定义，
  首次运行明确报无基线而不是猜一个数；两行状态（后台重建、索引行数与
  最后写入时间）是 Stellamem 自己的补充，原版没有
